# AntigravityProxyLauncher v2.8.2 For macOS x86_64 / arm64

**发布日期**：2026-11-27
**上一发布版本**：v2.8.1-macos（2026-11-26）

本次发布聚焦两件事：**让 Gemini 在没有 TUN 的条件下正常启动并联网**，以及**把本地网关变成一个真正常驻的后台服务**。同时补齐了一个 CLI 自检入口，并修掉了一批在真实机器上才暴露的稳定性问题。

---

## 🆕 新功能

### 1. Gemini 走纯回环 + SNI 分流（不再需要 TUN / pf）

**问题**：注入 dylib 后 Gemini 仍然打不开窗口。根因是 Gemini 的 gRPC 传输层走
`Network.framework`，它的 `connect()` 发生在 dyld 共享缓存内部，
`DYLD_INTERPOSE(my_connect, connect)` 拦不到；而 FakeIP 返回的 `198.18.x.x`
在没有 TUN 的环境里没有任何路由，连接直接失败，App 卡在 `isRecoveringFromError`。

**方案（三层，全程不碰 TUN、不碰 pf）**：

| 层 | 做法 |
|---|---|
| dylib | 对 Gemini 进程把 `getaddrinfo` 的返回值改写为 `127.0.0.1`（`fake_ip.bypass_cidr`，默认 `127.0.0.1/32`） |
| root 守护进程 `sni_redirect` | 监听 `127.0.0.1:443`，读取 TLS ClientHello 里的 SNI，经上游 SOCKS5 连到 `<SNI>:443` 做**纯隧道**转发（不解密、不装证书） |
| Launcher | 一次性管理员授权安装 `/Library/PrivilegedHelperTools/com.antigravity.sniredirect` 与对应 LaunchDaemon |

Antigravity / IDE 仍然使用 FakeIP（`198.18.0.0/15`），两条路径互不影响。

### 2. 本地网关常驻，只有一个开关

网关是 Launcher 的固定组成部分，装了应用就有网关。用户只有一个选择：

> 退出 Launcher 后，网关是继续运行，还是跟着关闭？

偏好设置 → 本地网关 (18081) → **退出 Launcher 后保留网关（继续对外提供模型服务）**

| 开关 | `RunAtLoad` | `KeepAlive` | 退出 Launcher 后 |
|---|---|---|---|
| 勾选（默认） | `true` | `{ SuccessfulExit: false }` | 网关继续监听 `127.0.0.1:18081` |
| 不勾选 | `false` | `false` | 网关一起关闭 |

旁边的**重启网关**按钮是唯一的手动操作。

### 3. 路由规则热重载：保存不重启，长连接不断

改模型映射规则时不再重启网关进程，改为给进程发 `SIGHUP`，
由 `atomic.Pointer[config.RoutingConfig]` 原子替换配置、Provider 注册表整份重建后一次性换入。

```
[MITM] routing config hot-reloaded (no restart)
```

进程 pid 不变，正在进行的 SSE 流不受影响。

### 4. 新增 CLI 自检与运维命令

```bash
AntigravityProxyLauncher --verify-all        # 逐个目标检查 Antigravity / IDE / Gemini / agy / claudeCode / codex
AntigravityProxyLauncher --restart-gateway   # 按最新配置重启网关并做健康检查
```

`--verify-all` 会跳过未安装的目标，任一目标异常时以非零退出码返回，方便脚本化。

## 🐛 修复

### 切换 tab 时误报「需要修复」

两个独立缺陷叠加：

1. dylib 校验和永远读的是 CLI 那份 dylib，导致 Antigravity / IDE 的校验结论互相污染；
2. 修复元数据在 `codesign` **之前**写入，落盘的是未签名哈希，签名后必然对不上。

修复方式：按目标类型读对应 dylib 的校验和；元数据写入移到重签名之后；
ad-hoc 签名本身不确定（同一份代码重新签名哈希会变），因此追加 Mach-O `LC_UUID` 作为回退判据。

### 改了上游代理端口，Gemini 却连不上

`sni_redirect` 的 LaunchDaemon plist 里 `-socks5` 写的是旧端口。
现在安装前会比对已装 plist 里的值与当前配置：二进制变了、或上游变了，都会重装更新；
健康检查也会主动提示「本地 SNI 分流器的上游代理与当前配置不一致，请重新修复」。

### 重新打开 Launcher 会切断正在进行的请求

两个原因：

1. `startProxy()` 无条件先回收 18081，把 launchd 托管的网关 `SIGTERM` 掉；
2. 更隐蔽的一层：网关的 `EnvironmentVariables` 之前是把整个 `ProcessInfo.environment`
   原样写进 plist，而从 Finder / `open` / 终端启动继承到的环境并不相同
   （`XPC_FLAGS`、`__CFBundleIdentifier` 等），plist 每次都不一样，
   于是"plist 没变就复用"的快速路径永远命中不了，每次开 Launcher 都重载一次。

现在只在 launchd 没跑、端口被孤儿进程占着时才回收；网关环境改为显式白名单，
plist 变成确定的。重开 Launcher 网关 pid 不变。

### 其它

- 设置页在 `body` 里同步 spawn `launchctl`，每次重绘跑 6 个子进程 → 改为异步快照 + `@State` 缓存
- 读取 dylib UUID 用 `/usr/bin/dwarfdump`，未装 Command Line Tools 的机器会弹安装框 → 换成原生 Mach-O 解析
- `sni_redirect`：SOCKS5 握手失败分支未关闭 socket、双向 `io.Copy` 未做半关闭导致 goroutine 泄漏、域名长度未校验 255 上限、`server_name` 类型未校验
- 网关在透传模式下被 `SIGHUP` 直接杀掉 → 显式忽略
- Provider 注册表重建时长时间持写锁（工厂调用可能含网络请求）→ 改为局部构建后一次性换入

## ⚠️ 升级提示

**本次 dylib 有变更，升级后请对 Antigravity / IDE / Gemini 各执行一次「修复」。**
Launcher 会在对应 tab 显示「需要修复」，`--verify-all` 也会报出 drift。

勾选「退出后保留网关」的用户，升级后无需手动处理网关；
未勾选的用户重新打开 Launcher 即可。
